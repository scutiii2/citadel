# Council Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement task-by-task, or superpowers:subagent-driven-development if the user chooses delegation. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Centralize Laya model ownership in `apps/council/`, provide reproducible offline training, and migrate existing callers individually without changing their workflow policy.

**Architecture:** Council performs one native typed prediction per authenticated HTTP request, with one model pool and bounded serialized execution. Offline commands create and evaluate immutable bundles. Garrison keeps triage/Router voting, thresholds, remote fallback and consumer-facing contracts.

**Tech Stack:** Python >=3.11, FastAPI, Uvicorn, Pydantic 2, HTTPX, pinned Laya/PyTorch; optional Hugging Face datasets/Hub, NumPy, SciPy and scikit-learn for training.

**Spec:** [Council design](../specs/2026-10-22-council-design.md). Read it before implementing. Both documents are drafts for user review; no implementation, full training or deployment is initiated by this plan.

## Global constraints

- Project: `apps/council/`, independent `.venv_council`; Python >=3.11; no cross-project source imports.
- Default bind: `127.0.0.1:8080`, configurable with `COUNCIL_HOST`/`COUNCIL_PORT`; Docker internal bind `0.0.0.0:8080`.
- One Uvicorn worker, one execution slot, 32 waiting requests; service/training use one OS-backed lock under the same configured `data/` root.
- Every standalone command that loads/executes models takes the same lease; promotion/rollback refuse while serving. Capture embedded parity before starting Council, rather than loading both together.
- `/v1/*` requires `X-Internal-Token` with `INTERNAL_API_TOKEN`; missing configured token fails startup. Only `/health` is public liveness.
- Prediction deadline: default 10,000 ms, valid 1-30,000 ms, including queue/validation/compute; late compute retains its slot until it actually ends.
- Request bounds: 256 KiB body, 64,000 text characters, 128-character IDs, 4,000-character instruction/criterion fields; 1-8 questions, 2-32 options/levels, max_len 512-8,192 subject to bundle capability.
- Existing Garrison public limits remain eight questions, 2-10 options and 4,000 text characters. Use its configured triage window, currently default 4,096.
- Native requests preserve every option and full state; overflows fail visibly. Exact choices and numerical prediction parity within 1e-5 are required on matched runtime/device/precision.
- Startup/prediction never download models. Preparation, full training, promotion, publishing and deployment are explicit operator actions.
- Garrison retains current voting mathematics, typed-question behavior and local-only restrictions. No silent embedded fallback on Council failure.
- Data/bundles/runs are ignored runtime state; keep source revisions, hashes, splits and model provenance in manifests. No raw request logging or automatic training capture.
- Preserve existing unrelated changes. Check the reuse catalog before implementing new reusable Garrison/Armory helpers; do not read credentials or key files as part of exploration.

## Review focus

- Multiple agent processes and profile aliases must share one actual model owner; test in Tasks 2-4 and 12.
- Timed-out/disconnected requests must not free capacity while native work continues; test queue fairness and shutdown in Tasks 3-4.
- Native yes/no order, scalar score semantics, tokenizer overflow and inherited temperatures can silently change answers; test in Tasks 2, 6-9.
- Duplicate benchmark groups, aggregate/subset imports and checkpoint exposure can invalidate evaluation; test provenance and split exclusion in Tasks 5 and 7.
- Partial rollout and Council outages must retain local-only behavior, Router abstention and advisory no-suggestion behavior; test in Tasks 8-10 and 12.

ownership after rollout evidence. Code may be prepared before live checks, but
do not mark a runtime migration complete without its check. If hardware, models
or deployment access is unavailable, leave the corresponding evidence gate open.

For each task, run its meaningful red/green test cycle before moving on; commit
only task-owned files when the selected execution workflow calls for commits.
Never include unrelated worktree edits. Use the project's own Python environment.
