# Plan 5.5: Share links move to Stronghold

Branch: `refactor/stronghold-shares`.

## What moved

1. Stronghold `src/shares/`: the links (Treasury collection `shared_chats`, one document per link, keyed by the SHA-256 of the token), the 50-active-links limit, expiry, and the routes `POST /shares`, `GET /shares`, `DELETE /shares/{id}`, `POST /shares/revoke`, `GET /shares/public/{token}`, `DELETE /shares/accounts/{uid}`. Stronghold logs `share.create` and `share.revoke`.
2. Portcullis keeps what belongs with the chats: `snapshot_messages` (the rules for what a link may show), the login and permission checks, the per-address rate limit and the no-cache headers of the public read. It sends Stronghold the finished snapshot.
3. The public read calls Stronghold with no requester at all (`StrongholdForwarder.forward(..., None)`): only the internal token goes on it.
4. Deleting chats revokes their links first: one chat, all chats, and a folder with its chats (`revoke_shares`). If Stronghold cannot do it, nothing is deleted (502): a deleted chat must never keep a working link.
5. Account delete purges the account's links through Stronghold (`admin.shares_purge` on failure).

## Accepted behavior changes

1. Existing links stop working: no migration (as decided), the links start empty. Anyone holding an old link gets "not found".
2. Expired links are removed when their owner makes a new link and when somebody reads them; no startup sweep any more (`purge_expired_shares` is gone). An expired link that is never read again and whose owner never shares again stays in Treasury as inert data.
3. Link ids are random numbers up to 2^31 now, not a counting sequence.
4. Deleting a chat, all chats or a folder now needs Stronghold (502 `Stronghold is unavailable` otherwise). Before, it was one database transaction.
5. When Stronghold is down, `GET /api/shared/{token}` answers 502, not 404.
6. The old `shared_chats` table stays in Portcullis's database, unused.
